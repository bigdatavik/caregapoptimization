# caregapoptimization — Care-Gap Recommendation & Optimization

Medicare Advantage care-gap optimizer. It predicts each member × gap closure baseline (LR / LightGBM),
applies intervention-effect evidence and business policies, and solves a Pyomo/HiGHS MIP to pick
interventions under budget, vendor-capacity, and contact constraints. Packaged as an MLflow
pyfunc in Unity Catalog, with a FastAPI + static-HTML Databricks App. All data is synthetic.

## Conventions

- Never hard-code catalog, schema, host, user email, or warehouse ids. Add a bundle variable,
  then a widget, then a `CAREGAPOPTIMIZATION_*` env var in `src/config.py`.
- Any new notebook must copy the bootstrap block (project-root resolution + widgets) and be added to
  the job DAG in `databricks.yml`.
- Notebooks that need pyomo/highspy/lightgbm `%pip install` the pinned versions and then `%restart_python`.
  Keep the pins in sync across notebooks, `requirements.txt`, `environment.yml`, and notebook 08's
  `pip_requirements`.
- Notebook 11 must fail the job when pytest fails. Notebook 09 must fail when the model is missing.
- Always pass `--profile`. Never auto-select a profile.
- To refresh the evidence after a job run: `python scripts/export_run_outputs.py <run_id> --profile <P>`, then update `evidence/e2e_fresh_install_run.md`.

- Local runs that train LightGBM need OpenMP. On macOS without Homebrew `libomp`, point the loader at scikit-learn's bundled copy:
  `DYLD_LIBRARY_PATH=$(dirname $(find ~/.cache/uv -name libomp.dylib -path "*sklearn*" | head -1)) uv run ...`

## Known gaps in the prototype (verified against the code, 2026-10-24)

State these honestly in demos and docs; don't claim otherwise.
- **Baseline isn't in the objective.** The MIP maximizes `contract_weight × measure_weight × uplift`; `baseline_probability` is carried on candidates but unused.
- **The app doesn't use governed data or the model.** `app.py` generates its own 500 members in memory, passes `{}` baseline probs (every candidate defaults to 0.3), doesn't read UC or call the endpoint, and keeps feedback in memory. `/api/project-metadata` is mostly hard-coded and shows the default catalog/schema (`main` / `caregapoptimization`).
- **Contact cooldown never fires.** `build_candidates` doesn't carry `last_contact_date`, so `_apply_contact_cooldown` is a no-op outside its unit test.
- **Suppression rules suppress nothing on this data.** Only open gaps become candidates, and no `pending` gaps are generated.
- **Vendor capacity applies only when the config lists vendors.** Policy presets don't, so notebooks 05/06, the app and serving requests run without capacity limits; only notebook 07 sets them. The `vendor_capacities` table is written but never read. Only the first `ContactLimit` is applied.
- **Effects and labels are synthetic** (illustrative effect sizes; a linear synthetic label, so LR beats LightGBM).
- **DEMO_TRACK.md errors:** it calls $5K "a 62% budget cut" (it's 62% less spend than the $13.2K actually used), says the app reads the UC tables (it doesn't), and says measure weights shift the plan at $13.2K (they change only the objective there).

## Verified numbers (seed 42; for demos and docs)

- Data: 500 members, 1,007 gaps (858 open) → 3,432 candidates (858 × 4).
- Model (held-out, member-grouped split 770 / 237): AUC LR 0.6964 vs. LightGBM 0.5916; Brier 0.155 vs. 0.181.
- App / nb05, balanced, $13,200, no vendor caps: optimal, objective 160.8, 857 selected, $13,156, 0 violations (~13 s per app run; HiGHS itself < 1 s). At $5,000: 116.3, 625 actions, letters only, BPC dropped.
- nb07 with vendor caps (80 / 500 / 30 / 60): capacity binds at 670 actions and $13,200 even with $50K–$150K budgets; $5K keeps 81% of the value.
- Scenario Lab in the app runs scenarios sequentially (~13 s each); "late year conservative" is minimize-cost to a target of 5 (≈ $144, 18 actions).
- Best single notebook for a short end-to-end demo: **05** (show the recorded task output from the job run page rather than running it live).
